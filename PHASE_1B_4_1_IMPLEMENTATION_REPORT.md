## 1. Executive Summary

Phase 1B.4.1 (Stage 14.1 of the Approved Mixed-Model Query Safety Blueprint) has been implemented and verified.

The core objective of this phase is to establish database-layer embedding-model-aware filtering at vector retrieval time, enforcing strict cryptographic/semantic isolation between disparate embedding spaces (`nomic-embed-text` vs `gemini-embedding-2`) while preserving backwards compatibility for legacy documents that have `NULL` or unpopulated embedding-model metadata.

All required invariants (§2 of the Phase 1B.4.1 authorization) have been fulfilled:
- **Invariant A (Embedding Compatibility):** A query vector generated by one embedding model is never compared against or ranked with vectors generated by an incompatible model.
- **Invariant B (Legacy Ollama Compatibility):** Records with `NULL` or legacy metadata remain retrievable under Ollama query semantics and are strictly excluded from Gemini query semantics.
- **Invariant C (Gemini Isolation):** Gemini queries select exclusively chunks whose parent document has `d."embeddingModel" = 'gemini-embedding-2'`. All `NULL` and Ollama records are excluded.
- **Invariant D (Workspace Isolation):** Dual-clause workspace filtering (`c."workspaceId" = $1 AND d."workspaceId" = $1`) is preserved without modification.
- **Invariant E (Lexical Search Isolation):** Keyword full-text search (`searchKeywordChunks`) remains completely model-independent, ensuring all completed documents remain discoverable via BM25/FTS regardless of embedding model.

No schema modifications, database migrations, re-embedding runs, or production provider switches occurred in this phase.

## 3. Architecture & Implementation Details

### 3.1 Single Source of Truth: `EmbeddingModelPolicy`
Located in `packages/shared/src/embedding-policy.ts`:
```typescript
export const APPROVED_EMBEDDING_MODELS = {
  OLLAMA_NOMIC: 'nomic-embed-text',
  GEMINI_PRIMARY: 'gemini-embedding-2',
} as const;

export interface ModelFilterPolicy {
  targetModel: string;
  allowNullModel: boolean;
  isRecognized: boolean;
}

export class EmbeddingModelPolicy {
  public static resolveFilterPolicy(modelName?: string | null): ModelFilterPolicy {
    if (!modelName || modelName === APPROVED_EMBEDDING_MODELS.OLLAMA_NOMIC) {
      return {
        targetModel: APPROVED_EMBEDDING_MODELS.OLLAMA_NOMIC,
        allowNullModel: true,
        isRecognized: true,
      };
    }
    if (modelName === APPROVED_EMBEDDING_MODELS.GEMINI_PRIMARY) {
      return {
        targetModel: APPROVED_EMBEDDING_MODELS.GEMINI_PRIMARY,
        allowNullModel: false,
        isRecognized: true,
      };
    }
    return {
      targetModel: modelName,
      allowNullModel: false,
      isRecognized: false,
    };
  }

  public static isDocumentCompatible(
    queryModel: string | null | undefined,
    docEmbeddingModel: string | null | undefined,
  ): boolean {
    const policy = this.resolveFilterPolicy(queryModel);
    if (!policy.isRecognized) return false;
    if (docEmbeddingModel === policy.targetModel) return true;
    if (policy.allowNullModel && (docEmbeddingModel === null || docEmbeddingModel === undefined)) {
      return true;
    }
    return false;
  }
}
```

### 3.2 Parameterized SQL Construction: `buildVectorSearchQuery`
Located in `apps/api/src/lib/db.ts`:
```typescript
export function buildVectorSearchQuery(
  workspaceId: string,
  queryVector: number[],
  options?: SearchVectorChunksOptions,
): BuiltVectorSearchQuery {
  const topK = Math.min(Math.max(options?.topK || 10, 1), 50);
  const vectorStr = `[${queryVector.join(',')}]`;

  let conditions = `c."workspaceId" = $1 AND d."workspaceId" = $1 AND d."status" = 'COMPLETED' AND c."embedding" IS NOT NULL`;
  const params: any[] = [workspaceId, vectorStr, topK];
  let paramIndex = 4;

  const policy = EmbeddingModelPolicy.resolveFilterPolicy(options?.embeddingModel);

  if (!policy.isRecognized) {
    conditions += ` AND d."embeddingModel" = $${paramIndex} AND false`;
    params.push(policy.targetModel);
    paramIndex++;
  } else if (policy.allowNullModel) {
    conditions += ` AND (d."embeddingModel" = $${paramIndex} OR d."embeddingModel" IS NULL)`;
    params.push(policy.targetModel);
    paramIndex++;
  } else {
    conditions += ` AND d."embeddingModel" = $${paramIndex}`;
    params.push(policy.targetModel);
    paramIndex++;
  }

  // Parameter offsets for subsequent optional filters ($5, $6, ...)
  if (options?.documentIds && options.documentIds.length > 0) {
    conditions += ` AND c."documentId" = ANY($${paramIndex}::text[])`;
    params.push(options.documentIds);
    paramIndex++;
  }
  // ... fileTypes, pageStart, pageEnd ...

  const query = `
      SELECT 
        c."id", c."documentId", c."workspaceId", c."chunkIndex", c."content", c."tokenCount",
        c."pageStart", c."pageEnd", c."metadata", c."createdAt",
        d."originalName" AS "docOriginalName", d."extension" AS "docExtension",
        d."status" AS "docStatus", d."pageCount" AS "docPageCount",
        (1 - (c."embedding" <=> $2::vector)) AS "similarity",
        (c."embedding" <=> $2::vector) AS "distance"
      FROM "document_chunks" c
      JOIN "documents" d ON c."documentId" = d."id"
      WHERE ${conditions}
      ORDER BY c."embedding" <=> $2::vector ASC
      LIMIT $3
    `;

  return { query, params };
}
```

## 6. Performance Considerations & HNSW Index Interaction

1. **HNSW Vector Post-Filtering:**
   - In PostgreSQL with `pgvector`, adding a `WHERE` condition on a joined table (`JOIN documents d ON c."documentId" = d."id" WHERE d."embeddingModel" = $4`) executes vector search with post-filtering.
   - For workspaces with high chunk density, `hnsw` index traversal continues to operate efficiently because `c."workspaceId"` and `d."workspaceId"` constrain the search space.
   - In Stage 14.1, no partial index or schema alterations are introduced. In a future production migration (Stage 15), if corpus sizes exceed $10^5$ chunks per workspace, a dedicated model index or denormalized `c."embeddingModel"` can be evaluated without any breaking API changes.

2. **Parameter Offset Safety:**
   - Dynamically constructed parameters in `buildVectorSearchQuery` use an incrementing index starting at `$4` (with `$1 = workspaceId`, `$2 = vectorStr`, `$3 = topK`).
   - Every condition (`embeddingModel`, `documentIds`, `fileTypes`, `pageStart`, `pageEnd`) accurately appends to `params` and increments `paramIndex`. No parameter mismatch or off-by-one errors can occur.

# MindVault — Embedding Compatibility & Model Policy

**Version:** 1.0  
**Phase:** Phase 3 (Retrieval Engine & Hybrid Search)  
**Status:** Mandatory Architectural Invariant

---

## 1. Overview & Policy Rationale

Vector embeddings represent high-dimensional projections of textual semantics within a latent space specific to a given model architecture, training objective, tokenizer, and coordinate geometry.

**Fundamental Theorem of Vector Retrieval:**  
Two embedding models producing vectors of the same dimension (e.g. 768) are **not** interchangeable. Vector similarity calculations (such as cosine distance) between an embedding generated by Model A (e.g., `nomic-embed-text`) and a document chunk embedded by Model B (e.g., `text-embedding-004` or `bge-base-en`) are mathematically meaningless and produce arbitrary, corrupt retrieval rankings.

To guarantee evidence-grounded retrieval integrity, MindVault strictly enforces this Embedding Compatibility Policy.

---

## 2. Invariant Specifications

### 2.1 Canonical Embedding Configuration

- **Model Name:** `nomic-embed-text` (v1.5)
- **Model Provider:** Ollama (default endpoint: `http://localhost:11434`)
- **Vector Dimension:** Exactly **768**
- **Distance Metric:** Cosine Distance (`vector_cosine_ops` in pgvector)
- **Test Mode Fallback:** `MockEmbeddingProvider` (producing normalized 768-dimensional vectors from deterministic SHA-256 seed hashing).

### 2.2 Prohibited Actions

1. **Silent Fallback:** The retrieval engine must NEVER silently switch to another model (such as a generic API or alternative cloud model) when the primary provider fails or returns an error.
2. **Dimension Coercion:** Truncating or zero-padding vectors to match 768 dimensions is strictly forbidden.
3. **Cross-Model Querying:** Never compute similarity between query embeddings and document embeddings generated by distinct models.

## 3. Compatibility Validation Rules

Every retrieval request undergoes runtime compatibility verification:

```
[Query Input]
      │
      ▼
[Embedding Generation] ──> Model: M_query, Dim: D_query
      │
      ▼
[Dimension Check] ───────> Is D_query == 768?
      │                    NO  ──> HTTP 500 / 422 "Embedding dimension mismatch"
      │                    YES
      ▼
[Model Identity Check] ──> Does M_query match target documents in Workspace?
                           NO  ──> Actionable Error: "Incompatible embedding model"
                           YES
      │
      ▼
[Execute Vector Search]
```

### 3.1 Document Metadata Verification

In MindVault, every document record in PostgreSQL contains:

- `embeddingModel`: The model string used during ingestion (e.g. `nomic-embed-text` or `mock-embed-768`).
- `embeddingDimension`: The integer dimension recorded during chunking (e.g. `768`).

During retrieval:

- If a workspace contains indexed documents whose `embeddingModel` or `embeddingDimension` differs from the active query embedding provider, the retrieval engine detects the discrepancy and rejects the search or restricts candidate documents to matching models, emitting a warning in the response metadata.

### 3.2 Actionable Error Handling

When a model or dimension mismatch is detected, the API returns a structured, clear error payload:

```json
{
  "success": false,
  "error": {
    "code": "EMBEDDING_MODEL_MISMATCH",
    "message": "Query embedding model 'text-embedding-004' (dim: 768) is incompatible with workspace document embeddings generated with 'nomic-embed-text' (dim: 768). Re-indexing is required to switch models."
  }
}
```

---

## 4. Re-Indexing Migration Protocol

If the platform introduces a new embedding model in the future:

1. **Never mutate embeddings in-place** without version tracking.
2. Store the model version identifier alongside every chunk (`chunk.metadata.embeddingModelVersion`).
3. Maintain dual embeddings during transition periods, or execute an explicit workspace re-indexing job that re-processes all original documents stored in object storage.
4. Update the pgvector index only after all documents within the workspace have been re-embedded.

---

## 5. Compliance Checklist

- [x] Query embeddings use the identical `EmbeddingProvider` abstraction as ingestion.
- [x] Vector dimension is validated before query execution (must equal 768).
- [x] No automatic or silent substitution of third-party cloud embeddings.
- [x] Deterministic mock provider is isolated strictly to `NODE_ENV === 'test'`.
- [x] Mismatches produce actionable, explicit errors rather than empty or nonsense results.
